# smol-gitstat-web design

This document defines the design and architecture of smol-gitstat-web, a buildless rewrite of
gitstat-web. The original React implementation is kept in `old/` as a reference until the new
version reaches feature parity, then it will be removed. `old/ARCHITECTURE.md` describes the
original in depth.

## 1. Goal and principles

smol-gitstat-web visualises the history of a git repository from a JSON file produced by
[smol-gitstat](https://github.com/samal-rasmussen/smol-gitstat). It shows activity over time as a
stacked line chart, a share-of-total pie chart, a summary table, and a browsable commit list, with
grouping by author, project or file type and configurable filters.

Principles, in priority order:

1. **Buildless.** The repository is the deployable artifact. `index.html` runs as-is from any
   static file server. No bundler, no transpiler, no CSS preprocessor.
2. **Minimal moving parts.** Three vendored runtime libraries, five dev tools, four config files.
   Anything else must justify itself against "could a few lines of our own code do this".
3. **Private by design.** Uploaded data never leaves the browser.
4. **Typed and tested without a build.** JSDoc types checked by `tsc`, pure logic tested under
   Node's built-in test runner, the UI tested with Playwright.
5. **Practical UX.** Feature complete relative to the original, simplified where the original
   was fussy, improved where the original was awkward. Not a visual clone.

## 2. Scope

### Kept from the original

- Upload a JSON file by drag-and-drop or file picker, or load a bundled sample.
- Graphs: line chart over time, pie chart, summary table.
  - Aggregations: commits, additions, deletions, mutations (additions + deletions),
    difference (additions − deletions).
  - Group by: author, project, file type (extension).
  - Time units: day, week, month, year.
  - Date range filter. Initial unit chosen automatically from the range.
  - Smallest series folded into an "Others" series above a data-point cap.
- Commits: sortable, paginated table with expandable per-file detail and per-commit exclusion.
- Config: include and exclude file path regexes, author aliases, exclude authors, exclude
  merge commits, exclude commits by hash. Config persists across reloads.
- About page.

### Changed

- **Data persists across reloads** in IndexedDB. The original kept nothing and required
  re-upload on every refresh. Data still never leaves the browser; there is a one-click
  "clear data" action.
- **View settings live in the URL** (hash query parameters) instead of sessionStorage, so a
  particular chart is shareable and bookmarkable.
- **One upload view** replaces the separate home and "change data" screens.
- **Date basis is configurable**: committer date (default) or author date. Both timestamps are
  in the file.
- **Default date range** is first commit to last commit rather than first commit to today.
- **Authors are configured in one table** (name, commit count, merge-into, exclude) instead of
  separate alias and exclusion widgets. Aliases are stored as a flat map from raw name to real
  name, which is both simpler and exactly the semantics the original enforced.
- **File filters are one regex per line in a textarea** instead of dynamic input rows.
- **Top navigation bar** instead of a collapsible side menu.
- **Light and dark theme** follow the OS preference.
- **One bundled sample**, generated by running `npx smol-gitstat` in this repository, replaces
  the 22 MB of React and Helm samples.

### Dropped

- Markdown rendering of commit bodies. Bodies are kept and shown as plain text.
- The "(86% similar)" label on renamed files and the rule excluding files at 100% similarity.
  Both existed to cope with the Go tool, which emitted a rename as two entries with the new
  path counted as fully added. smol-gitstat emits one entry with the diff against the old
  content, so a pure move is already 0 / 0 and needs no rule. In the old samples the rule
  never excluded a single line. Renames themselves are kept: the file table shows the old
  path from `renameOf`.
- Raw (unfiltered) line totals. The original computed them but never displayed them.
- Microsoft Edge warning.

## 3. Runtime dependencies

All three are vendored as single files in `vendor/`, pinned by version in the file header, and
loaded from `index.html`. No CDN, no import map.

| Library | Version | File | Loaded as |
|---|---|---|---|
| Alpine.js | 3.17.2 | `vendor/alpine.esm.js` (from `alpinejs/dist/module.esm.js`) | ES module import from `js/app.js`, started explicitly with `Alpine.start()` |
| Chart.js | 4.5.1 | `vendor/chart.umd.js` (from `chart.js/dist/chart.umd.js`) | Classic `<script>`; exposes the `Chart` global with all controllers registered |
| Pico CSS | 2.1.1 | `vendor/pico.min.css` (from `@picocss/pico/css/pico.min.css`) | `<link rel="stylesheet">` |

Why these forms:

- Alpine is imported as a module so that directives, stores and components are registered before
  `start()`, which the Alpine docs require. The CDN build auto-starts in a microtask and would
  race our registration.
- Chart.js's ESM build imports from a `chunks/` folder and requires manual registration of
  controllers. The UMD build is one file and registers everything.
- Pico's class variant (not classless) is used because `.container` and `.grid` are wanted.
  Pico switches to its dark palette under `prefers-color-scheme: dark` automatically.

Types for the vendored files come from npm dev dependencies (see section 12) via a sibling
declaration file `vendor/alpine.esm.d.ts` and a global declaration for `Chart`.

```html
<!doctype html>

```

Deferred classic scripts and module scripts execute in document order after parsing, so
`Chart` exists before `app.js` runs. The empty `x-data` on `<body>` is required: Alpine only
initialises trees rooted at an `x-data` element, so without it neither `x-view` nor the nav's
`x-text` would ever run. The nav links carry their icons as `<span class="icon icon-<name>">`
spans per section 11.

### 5.2 Boot sequence (`js/app.js`)

1. Import Alpine from `../vendor/alpine.esm.js`.
2. Register the `x-view` directive, the `app`, `router` and `config` stores, and the four
   view components.
3. Load the persisted config from localStorage into the config store.
4. Open IndexedDB and, if a dataset is stored, load it into `dataset.js` and bump
   `$store.app.dataVersion`.
5. Start the router (parse the current hash, listen to `hashchange`).
6. `Alpine.start()`.

Steps 4 and 5 are awaited before `start()` so the first render already knows whether data exists.

### 5.3 Router (`js/router.js`)

Hash-based, so it works on any static host with no rewrite rules. A location looks like
`#/graphs?unit=month&by=author&agg=commits&from=2020-01-01&to=2020-12-31`.

- `$store.router.view` is the path segment: `upload` (for `/` and `/upload`), `graphs`,
  `commits`, `config`, `about`. Unknown paths redirect to `/`.
- `$store.router.query` is a plain object of the query parameters.
- `router.navigate(view, query)` writes the hash; `router.setQuery(patch)` merges parameters
  into the current hash with `history.replaceState` so slider-style changes do not flood the
  back stack.
- **Guard:** if no dataset is loaded, `graphs`, `commits` and `config` redirect to `upload`.

### 5.4 View loading (`js/view.js`)

```js
Alpine.directive('view', (el, { expression }, { effect, evaluateLater }) => {
  const getName = evaluateLater(expression)
  effect(() => getName(async name => {
    const html = await loadView(name)          // fetch('views/' + name + '.html'), cached in a Map
    Alpine.nextTick(() => { el.innerHTML = html })
  }))
})
```

Alpine's mutation observer initialises the injected markup. `nextTick` keeps the injection
outside Alpine's own mutation phase. Views contain no `<script>` tags because the browser would
not execute them; every view's root element declares `x-data="<name>View"` referring to a
component registered from `js/views/`.

Fetching requires an HTTP server, which the dev script provides (section 12).

## 6. Data model

### 6.1 Input format

Produced by smol-gitstat. All timestamps are ISO 8601 strings with offset.
`message` is the subject line, followed by a blank line and the body when the commit has one.
Binary files have `isBinary: true` and zero counts. Renamed files carry the new path in
`filepath` and the old path in `renameOf`.

Two limitations of the input shape the app. smol-gitstat reads `git log --numstat`, which
gives no similarity score for renames, so none is shown; a pure rename arrives with zero
additions and deletions and contributes nothing on its own. And `git log` prints no diff
for merge commits, so they arrive with an empty `files` array. The "include merge commits"
setting therefore only affects the commit count aggregation, and its help text says so.

```json
{
  "version": "1.0.0",
  "projects": [{
    "name": "repo-folder-name",
    "commits": [{
      "hash": "515326753b15eb247493b1b5c657eee1bc515337",
      "author":    { "name": "Jane Doe", "time": "2020-04-29T19:14:15+01:00" },
      "committer": { "name": "Jane Doe", "time": "2020-04-29T19:14:15+01:00" },
      "message": "Subject line\n\nOptional body, possibly several paragraphs.",
      "isMerge": false,
      "files": [{
        "filepath": "src/index.js",
        "renameOf": "lib/index.js",
        "isBinary": false,
        "additions": 23, "deletions": 10,
        "rawAdditions": 23, "rawDeletions": 10
      }]
    }]
  }]
}
```

Validation on load is shallow and deliberate: the top-level shape, that `projects` is an array,
that each commit has `hash`, `author.time`, `committer.time` and a `files` array. Anything else
is trusted. A failed validation shows an error on the upload view with the reason. Unused
fields (`rawAdditions`, `rawDeletions`, and the old generator's `email`, `renameTo`,
`similarity`) are ignored.

Files generated before smol-gitstat added rename support have rename paths in git's own notation, `old => new` or
`prefix{old => new}suffix`, and no `renameOf`. The extend step normalises these to the new
path so older files keep working.

### 6.2 Types (`js/types.d.ts`)

Ambient interfaces so JSDoc can reference them without imports.

```ts
interface Signature { name: string; time: string }
interface CommitFile {
  filepath: string; renameOf?: string; isBinary: boolean
  additions: number; deletions: number
}
interface Commit {
  hash: string; author: Signature; committer: Signature
  message: string; files: CommitFile[]; isMerge: boolean
}
interface Project { name: string; commits: Commit[] }
interface GitStatData { version: string; projects: Project[] }

interface ExtendedFile extends CommitFile { excluded: boolean } // filepath normalised
interface ExtendedCommit {
  hash: string; project: string
  author: string                 // alias-resolved
  committer: string              // alias-resolved
  time: number                   // epoch ms of the configured date basis
  title: string                  // first line of message
  body: string                   // rest of message, trimmed; empty if none
  isMerge: boolean
  files: ExtendedFile[]
  additions: number; deletions: number // filtered totals
  excluded: boolean
}

type Aggregation = 'commits' | 'additions' | 'deletions' | 'mutations' | 'difference'
type GroupBy = 'author' | 'project' | 'filetype'
type TimeUnit = 'day' | 'week' | 'month' | 'year'
type DateBasis = 'committer' | 'author'

interface Config {
  dateBasis: DateBasis                   // 'committer'
  includeMergeCommits: boolean           // false
  includeFilePatterns: string[]          // []  (empty means include everything)
  excludeFilePatterns: string[]          // []
  aliases: Record<string, string>        // raw name → real name
  excludeAuthors: string[]               // real names
  excludeCommits: string[]               // hashes
}

interface Group { name: string; commits: ExtendedCommit[]; total: number; average: number }
interface Series { name: string; values: number[]; color: string }
```

`time` is precomputed as a number so sorting, filtering and bucketing never re-parse strings.

## 7. State and reactivity

### 7.1 The reactivity boundary

Alpine stores and `x-data` objects are deep reactive proxies. Wrapping a dataset of tens of
thousands of commits and hundreds of thousands of file entries would make every access slow.
Therefore:

- **`js/dataset.js` is a plain module, not a store.** It holds `raw: GitStatData | null` and
  `commits: ExtendedCommit[]` in module-level variables and exposes `load(data)`, `clear()`,
  `rebuild(config)` and getters. Nothing in it is reactive.
- **`$store.app` holds only small values:** `dataVersion` (incremented on load, clear and
  rebuild), `projectName`, `commitCount`, `firstTime`, `lastTime`, `sizeBytes` (of the
  uploaded JSON text, for the upload card), `summary` (a short string for the nav).
- **View components read the dataset through functions** in their `init()` and in
  `$watch('$store.app.dataVersion')` and query watchers, then assign small derived results
  (a few series arrays, a page of commits) to their own reactive state.

This keeps Alpine's proxies over data measured in kilobytes, never megabytes.

### 7.2 Config store (`js/config.js`)

`Alpine.store('config', ...)` with the `Config` shape plus `save()` and `reset()`.
`Alpine.effect` serialises it to `localStorage['config']` on change. On startup the stored value
is merged over the defaults so new keys get defaults. After any config change, `dataset.rebuild`
runs and bumps `dataVersion`.

### 7.3 Dataset persistence (`js/db.js`)

One IndexedDB database with one object store and one key. `get()`, `set(record)`, `clear()`.
The record — the parsed object plus its byte size, `{ data, sizeBytes }` — is stored by
structured clone, which is faster than re-parsing text and has no size ceiling in practice. The upload view's "clear data" button calls `clear()` and
`dataset.clear()`.

### 7.4 URL state

| View | Parameters | Defaults |
|---|---|---|
| graphs | `agg`, `by`, `unit`, `from`, `to` | `commits`, `author`, auto, first commit, last commit |
| commits | `sort`, `page`, `per` | `time`, `1`, `50` |

Dates are `YYYY-MM-DD` in local time. Missing or invalid parameters fall back to defaults
without rewriting the URL; only user changes write to it.

## 8. Compute pipeline (`js/compute/`)

Pure ES modules with no imports from Alpine, the DOM or `dataset.js`. Every function takes and
returns plain data, so they run unchanged under Node for unit tests.

### 8.1 `extend.js`: `extendCommits(data, config) → ExtendedCommit[]`

For every commit of every project:

1. Resolve author and committer through `config.aliases`.
2. Skip the commit entirely if the resolved author is in `excludeAuthors`.
3. Normalise each file path: if `renameOf` is absent and the path matches git's rename
   notation (`old => new` or `prefix{old => new}suffix`), set `filepath` to the new path and
   `renameOf` to the old one. Current smol-gitstat output is already in this shape.
4. Compile the include and exclude patterns once (invalid regexes are reported, not thrown,
   and skipped). For each file: excluded if any exclude pattern matches, or include patterns
   are non-empty and none match. Patterns are tested against the normalised new path.
5. Sum `additions`/`deletions` over non-excluded non-binary files.
6. `excluded` is true if the hash is in `excludeCommits`, or it is a merge and merges are
   not included, or it is not a merge and no file survived step 4 with line changes. When the
   commit is excluded every file is marked excluded too and the totals are set to zero.
   An excluded commit contributes nothing to any aggregation, including the commit count,
   but it stays in the list so the commits view can show it dimmed. The third rule matches the
   original, where a commit with nothing left after filtering did not count as a commit; it is
   restricted to non-merges because merges from smol-gitstat never carry files, and the
   "include merge commits" setting would otherwise have no effect.
7. `time` is `Date.parse` of the configured basis. `title` is the first line of `message` and
   `body` is the remainder after the blank line.

Result sorted ascending by `time`. Runs once per dataset load or config change.

### 8.2 `group.js`: `groupCommits(commits, by) → Group[]` (without totals)

`author` and `project` map one commit to one group. `filetype` splits a commit by file
extension into one shallow copy per extension, each with only that extension's files and
recomputed totals, so a commit touching `.js` and `.css` counts once in each of those groups
under the commits aggregation, as in the original. Extension is the text after the last dot in the last path segment, or
`(none)`.

### 8.3 `aggregate.js`

- `aggregator(agg) → (commit) => number`.
- `totals(groups, aggregator, periods) → Group[]` fills `total` and `average` and sorts
  descending by total.

### 8.4 `time.js`

Native `Date` in local time. `startOf(ms, unit)`, `add(ms, unit, n)`, `bucketKey(ms, unit)`,
`label(ms, unit)`, `periodCount(from, to, unit)`, `autoUnit(from, to, max = 100)` (finest unit
with at most `max` periods). Weeks start on Monday.

### 8.5 `series.js`: `buildSeries(groups, aggregator, unit, from, to) → { labels, series, others }`

Produces the list of bucket labels for the range and, per group, a zero-filled `values` array of
the same length. If the total point count exceeds 2000, the smallest groups are folded into one
`Others` series until under the cap, and their names are returned in `others`.

## 9. Views and UX

Pico provides the look. Custom CSS is limited to chart containers, the dropzone, the commit
detail rows, the icon class and small alignment fixes.

### 9.1 Upload (`#/`)

- Heading and one sentence of purpose.
- Instructions: run `npx smol-gitstat` in a repository, then drop the resulting file here.
- A dropzone that is also a file input. Shows a progress state while parsing.
- A "Load sample" button that fetches `samples/smol-gitstat-web.json`.
  The sample is regenerated with `npx smol-gitstat --out samples/smol-gitstat-web.json` run
  at the repository root. It is generated last, once the rewrite is complete, so that it
  includes the history of the rewrite itself and the move of the original into `old/`,
  which doubles as a real rename example.
- Privacy note: data is stored only in this browser.
- If data is loaded: a card with project name, commit count, date range, size, and buttons
  "Go to graphs" and "Clear data".
- Errors from validation are shown inline.

Parsing happens after a `setTimeout(0)` so the progress state paints first.

### 9.2 Graphs (`#/graphs`)

- Controls in one `<fieldset class="grid">`: aggregation, group by, time unit, from, to. Native
  `<select>` and `<input type="date">`. Changing any control updates the URL.
- Full-width stacked line chart. Stacking is disabled when any value is negative, which only
  happens with `difference`.
- Below, a two-column grid: pie chart on the left, summary table on the right with Name, Total,
  Average per unit. Names folded into Others are marked.
- The date range is applied once: commits outside `from`..`to` are dropped before grouping,
  and the line chart, pie chart and summary table all show that same subset. "Average" is the
  group total divided by the number of periods in the range.
- Empty range or no matching commits shows a short message instead of empty charts.

### 9.3 Commits (`#/commits`)

- Controls: sort by (time, additions, deletions, mutations), per page (20, 50, 100), and a
  pagination control showing page x of y with previous and next buttons.
- Table: date, author, title, additions, deletions, merge icon. Excluded commits are dimmed.
- Clicking a row toggles a detail row beneath it: hash, project, an "Exclude this commit"
  checkbox, the commit body if there is one as plain text with line breaks preserved (no
  markdown rendering, which would need another library), and a file table with path,
  additions, deletions, excluded files dimmed. A renamed
  file shows its old path beneath the new one, and a binary file shows a "binary" marker
  instead of counts.
- Exclusion writes to the config store, which rebuilds the dataset. The row stays open.

### 9.4 Config (`#/config`)

One form, sections separated with headings, changes applied immediately and persisted.

- **General:** date basis (radio), include merge commits (checkbox, with help text noting that
  merges carry no line counts and so only affect the commit count aggregation).
- **Files:** two textareas, one regex per line, include and exclude. Help text explains that
  exclude wins and that empty include means everything. Invalid regexes are flagged beside the
  field.
- **Authors:** a table of every raw author name in the dataset with commit count, a "Merge
  into" text input with a datalist of known names, and an "Exclude" checkbox. This replaces the
  original alias and exclude-author widgets.
- **Excluded commits:** list of hashes with a remove button each and a "clear all" button.
- **Reset config** button at the bottom.

### 9.5 About (`#/about`)

Static: what it is, link to smol-gitstat, privacy statement, credit to the original gitstat
project and author, license.

## 10. Charts (`js/charts/`)

Each chart module exports `render(canvas, data, options)` that creates a `Chart` instance on the
first call and calls `chart.update()` with replaced datasets afterwards. Instances are stored in
a `WeakMap` keyed by canvas and destroyed on component teardown via Alpine's `destroy()` hook.

- Line chart: category x axis of bucket labels, stacked y axis unless negatives, `fill` to the
  previous dataset, legend hidden above 20 series, tooltip in index mode sorted by value with
  zeroes hidden above 10 series.
- Pie chart: slices sorted descending, legend hidden, tooltip shows value and percentage.
- Colours come from `palette.js`, applied after sorting so neighbouring series differ. Chart
  text and grid colours read Pico's CSS custom properties so both themes look right.

## 11. Styling

- Pico's default palette and typography. No custom fonts.
- `css/app.css` uses native nesting and Pico's custom properties. Expected size: under 100
  lines.
- Layout is `container-fluid` with a max width set in CSS so charts get room on wide screens.
- Responsive: Pico's grid collapses to one column below its breakpoint. Tables sit in
  `overflow-auto` wrappers.

### Icons and identity

The original's logo and twelve SVG icons are not carried over; the new project has its own,
deliberately minimal identity. The few graphics it needs live as real files in `assets/`,
never inline in markup.

- **Favicon:** `assets/favicon.svg`, hand-written, three ascending white bars on a rounded
  square in Pico's primary blue (`#0172ad`). The filled background keeps it legible on light
  and dark tab bars without a media query. It is the only brand mark; the nav shows the app
  name as text.
- **Icons** are individual SVG files copied from [Lucide](https://lucide.dev) (ISC licence,
  noted in `assets/icons/LICENSE`) into `assets/icons/`. No icon font, no icon package, no
  build step: one file per icon, used only where an icon makes the page clearer or nicer.
  Where they appear, always beside a text label unless the meaning is unmistakable:
  - Nav: `upload`, `chart-line` (Graphs), `git-commit-horizontal` (Commits), `settings`
    (Config), `info` (About).
  - Upload view: `upload` in the dropzone, `trash-2` on "Clear data".
  - Commits view: `git-merge` as the merge marker, `chevron-right` rotating to point down
    on an expanded row.
  - Config view: `x` on the remove buttons of the excluded commits list, `rotate-ccw` on
    "Reset config".
- **Applied with a CSS mask.** An `<img>` of an SVG cannot use `currentColor`, so each icon
  is a `<span class="icon icon-<name>">` with `background-color: currentColor` and
  `mask: var(--icon) center / contain no-repeat`. The per-icon classes setting `--icon` live
  in `css/app.css`, because a `url()` inside a custom property resolves against the
  stylesheet that defines it, not the document, so an inline `style` attribute would resolve
  icon paths inconsistently. The
  icon takes the surrounding text colour in both themes and sizes with the font. Decorative
  icons carry `aria-hidden`; standalone ones carry `aria-label`.
- **Text where text is better:** "Previous" / "Next" for pagination, and text markers for
  "binary" and "Others".
- **No external fonts.** The original loaded Google Fonts, which sent a request to a third
  party on every visit.

## 12. Tooling

Dev dependencies, all invoked through npm scripts:

| Tool | Purpose | Config |
|---|---|---|
| sirv-cli | static dev server | none |
| typescript | `tsc` type-checks JSDoc-annotated JS | `tsconfig.json` |
| @types/alpinejs, chart.js | types only, for the vendored libraries | |
| @types/node | types only, so `tsc` understands the `node:` imports in unit tests | |
| oxlint | linting | none; `old/` and `vendor/` are ignored via script flags |
| oxfmt | formatting | none; `old/`, `vendor/` and Markdown are excluded via path patterns |
| @playwright/test | end-to-end tests | `playwright.config.js` |

`package.json` scripts:

```json
{
  "dev":      "sirv . --dev --port 3000",
  "check":    "tsc",
  "lint":     "oxlint --ignore-pattern old --ignore-pattern vendor",
  "fmt":      "oxfmt . '!old/**' '!vendor/**' '!**/*.md'",
  "test":     "node --test 'tests/unit/**/*.test.js'",
  "test:e2e": "playwright test"
}
```

oxfmt has no ignore flag; it takes positional glob patterns, where a `!` prefix excludes.
It writes by default and checks with `--check`, so CI-style verification is
`npm run fmt -- --check`. `vendor/` is excluded from both tools because the vendored files
are third-party; Markdown is excluded so the formatter never churns `design.md` and
`plan.md`. The `old/` exclusions exist only while `old/` is kept and go away with it.

`tsconfig.json`: `allowJs`, `checkJs`, `noEmit`, `strict`, `target: ES2022`,
`module: ES2022`, `moduleResolution: bundler`, `esModuleInterop` (the `alpinejs` types use
`export =`), `lib: [ES2022, DOM, DOM.Iterable]`, `types: [node, alpinejs]`,
`include: [js, tests, vendor/*.d.ts]`. `vendor/alpine.esm.d.ts` re-exports the `alpinejs` types so
`import Alpine from '../vendor/alpine.esm.js'` is typed. `js/globals.d.ts` declares
`const Chart: typeof import('chart.js').Chart`.

JSDoc conventions: every exported function has `@param` and `@returns`; object shapes reference
the ambient types from `types.d.ts`; `@ts-expect-error` is preferred over `any`.

No live reload. Reload the page after edits. If it ever grates, a `--watch` script using
Node's `fs.watch` is the answer, not a bigger server.

## 13. Testing

- **Unit** (`tests/unit/`): `node:test` and `node:assert/strict`. Cover `time.js` (unit
  boundaries, week start, DST edges, period counts), `extend.js` (aliases, exclusions,
  regex filters, merge handling, date basis), `group.js` (file type splitting),
  `aggregate.js`, `series.js` (zero-fill, Others folding), and `router.js` query parsing.
- **End-to-end** (`tests/e2e/`): Playwright with Chromium, `webServer` running sirv on a
  test port. Scenarios: upload a fixture and land on graphs; change group-by and see the
  summary table change; open the commits page, expand a row, exclude the commit and see it
  dimmed; set an alias in config and see authors merge; reload and see data persisted; clear
  data and see the guard redirect.
- **Fixtures** (`tests/fixtures/`): a hand-written dataset of about twenty commits across two
  projects, three authors and several extensions, with one merge commit, one binary file, one
  rename with `renameOf`, and one rename in the older `prefix{old => new}suffix` notation.
  Unit tests run only on fixtures, never on real histories, so expected values are known.
- **Local development data** (`samples/local/`, gitignored): one realistic mid-sized
  dataset for checking the views by hand, with many authors, merges, renames, binaries and
  commit bodies, and enough commits that pagination and "Others" folding kick in. Alpine is
  the chosen repository: small to clone, a few thousand commits, and one of our dependencies.
  Generated with a full clone — not a blob-less one: `git log --numstat` needs blob contents,
  so a `--filter=blob:none` clone fetches every blob lazily over the network and takes
  effectively forever, while the full clone is 17 MB and the generator finishes in under a
  second:

  ```sh
  git clone https://github.com/alpinejs/alpine /tmp/alpine
  cd /tmp/alpine && npx smol-gitstat --out <repo>/samples/local/alpine.json
  ```

  The published smol-gitstat must include rename and body support; until it does, run the
  patched checkout directly instead of `npx`.
- **Performance data:** the old React sample in `old/static` (section 14). Nothing to fetch.

## 14. Performance targets and notes

- A large dataset such as the old React sample (13,000 commits, 16 MB, kept in `old/static`)
  must extend in well under a second and re-render graphs in under 100 ms after a control
  change on a laptop.
- `extendCommits` is the only pass over all files; everything after it works on the commit
  array and precomputed totals.
- Bucketing uses a `Map` from bucket key to index, never `Array.find` over buckets.
- Chart.js animations are disabled for datasets above a few thousand points.
- No web workers. If parsing ever needs to leave the main thread, `JSON.parse` in a worker is
  a contained change to the upload view.

## 15. Non-goals

- Server-side anything, accounts, sharing beyond copying a URL.
- Supporting the old Go generator's extra fields beyond tolerating them. Similarity scores
  are not modelled.
- Internationalisation. Dates use the browser locale through `Intl.DateTimeFormat`.
- A hosted deployment. Hash routing keeps the app deployable to any static host later without
  changes.
